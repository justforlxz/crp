# 验收用例集

## 一、这份用例集是干什么的

它把「产品功能能用」和「界面没跑偏」变成可以重复执行的检查。**任何任务收尾时都必须跑一次**，这不是可选项。

用例分四组：

| 组 | 前缀 | 查什么 | 需要环境 |
| --- | --- | --- | --- |
| 功能 | `FUNC-` | 产品能力是否真的工作 | 数据库 + 可选的 CRP 沙箱 |
| 界面 | `UI-` | 页面模块是否齐备、布局是否破、交互是否通 | 浏览器 + base URL |
| 边界 | `EDGE-` | 空数据、失败状态、异常输入 | 数据库 |
| 权限 | `SEC-` | 未登录拦截、凭据不外泄 | base URL |

## 二、怎么跑

```bash
pnpm test:acceptance          # 功能 + 边界 + 权限（不需要浏览器）
pnpm test:acceptance:ui       # 界面组（需要 BASE_URL 指向已部署实例）
pnpm test:acceptance -- -t FUNC   # 只跑某一组
```

实现约定：

- 用例文件放 `tests/acceptance/`，一个分组一个目录：`func/`、`ui/`、`edge/`、`sec/`。
- **测试名必须以用例编号开头**，例如 `FUNC-03 提测记录页签按状态过滤`。这样失败时能直接对上本文编号。
- 断言失败必须打印「编号、预期、实际」三项，不接受只报 `expected true to be false`。
- 界面组复用 `scripts/style-check` 里的 Playwright 启动方式，不新起一套浏览器管理。
- 界面组读取 `.agents/spec/design/modules.json`，不写第二份模块清单。

## 四、界面组

| 编号 | 用例 | 步骤 | 预期 |
| --- | --- | --- | --- |
| UI-01 | 模块门禁 | `pnpm check:modules` | 11 个页面条目全部「缺失：无」，全局齐备，样式表齐备 |
| UI-02 | 外壳参数 | 打开任意页，量侧栏与顶栏 | 侧栏 216px、顶栏 56px、内容区最大宽 1400px，误差 ≤1px |
| UI-03 | 页面标题在顶栏 | 逐页切换 | 顶栏标题随页变化，内容区没有重复的大标题 |
| UI-04 | 卡片容器参数 | 量任意 `.panel` | 圆角 12px，边框 1px `#e3e8ef`，阴影不超过 `0 1px 2px rgba(16,24,40,.04)` |
| UI-05 | 统计卡 | 打开工作台 | 四张卡一行（1440），数值 30px 等宽，图标块 38×38 圆角 10 |
| UI-06 | 表格表头吸顶 | 滚动长表格 | 表头停在顶部，底色 `#fafbfc`，字号 12px |

## 六、权限组

| 编号 | 用例 | 步骤 | 预期 |
| --- | --- | --- | --- |
| SEC-01 | 九页未登录拦截 | 不带 Cookie 请求九个页面路由 | 全部 307 跳 `/login?next=当前路径`，没有任何页面渲染数据 |
| SEC-02 | 曾是漏网的四页 | 不带 Cookie 请求 `/packages`、`/packages/new`、`/packages/<id>`、`/baselines` | 四个路径全部 307，不返回 200 |
| SEC-03 | 凭据不落明文 | 配置一份凭据后查库 | `UserCredential` 里只有密文，全表搜不到明文密码 |
| SEC-04 | 接口不回密码 | 请求凭据读取接口 | 响应里没有密码或密文字段，只有是否已配置、账号名、验证时间 |
| SEC-05 | 密文不可跨人挪用 | 把 A 的密文复制到 B 的行再解密 | 解密失败，不返回明文 |
| SEC-06 | 未配置不发请求 | 未配置凭据的用户点创建提测 | 提示去配置页，CRP 调用计数为 0 |
| SEC-07 | 环境变量里没有个人凭据 | `grep -r "CRP_USERNAME\|CRP_PASSWORD\|GERRIT_HTTP_PASSWORD"` 排除文档 | 代码与配置里没有引用，只剩迁移说明 |
| SEC-08 | 作业 token 不泄露 | 查看接口与页面响应 | 响应里不出现任何作业 token |

## 七、validator 的强制要求

每个任务的验收节点（`in_validator`）必须：

1. 执行 `pnpm test:acceptance`，有部署环境时再执行 `pnpm test:acceptance:ui`。
2. 在 `[Result]` 里贴出汇总行：总用例数、通过数、失败数与失败编号。
3. 有失败用例时判不通过，把失败编号与「预期 / 实际」写进结论，不要只说「大部分通过」。
4. 界面组没有环境时，必须写明「UI 组未执行及原因」，不能用功能组结果代替界面组。

## 八、维护规则

- 新增功能时先加用例，再加功能代码。
- 删除功能时同一次提交里删掉对应用例，并在 `[Result]` 说明删了哪几条。
- 用例编号一旦发布不复用。删掉的就空着。
- 本文与 `tests/acceptance/` 里的用例必须一一对应；出现无编号的测试或无用例的测试都算不合格。
