# 任务派发与唤醒纪律

## 一、为什么有这份文档

这个仓库由 Multica 的多张单协作推进。单与单之间靠「派单评论」和「定时唤醒」串起来，这两样一旦用错，代价是整轮重跑：取消 run、重新派单、再等四十分钟。

已经发生过三次，每次都是同一类错误。这份文档把规则和核对方法写下来，`AGENTS.md` 里有对应的四条硬规则。

## 二、三种角色

| 角色 | 是什么 | 谁来做 |
| --- | --- | --- |
| 容器单 | 只记录一轮工作的整体状态与收口条件，本身不产出代码 | 由我（PL）维护状态 |
| 执行单 | 一张单对应一次可交付的改动，有明确的文件边界与验收条件 | 派给 Coder / Reviewer / QA |
| 巡检唤醒 | 定时检查执行单有没有断，断了就重跑 | 挂在容器单上，但只发评论 |

**容器单不执行任何工作。** 它的「收口步骤」由 PL 在子单全部合并之后做，不由执行者开工。

## 三、四条纪律

### 1. 容器单不挂执行型唤醒

唤醒的指令会被当成任务去做。挂在容器单上的唤醒如果写了「完成收口五步」，执行者就会去执行容器单的收口，发现依赖未满足，把容器单置成 `blocked`。

正确做法：唤醒只挂到**真正要做事的单**上；巡检类唤醒挂在容器单上时，指令第一句必须是「你只做巡检，不要改代码，不要改本单状态」。

### 2. 巡检只发评论，不动状态

巡检的产物是一条评论，写清每张单的状态、run 状态、最后消息时间。**不修改被巡检单的状态，不碰它们的文件。**

状态只由 PL 根据交付证据推进。巡检改状态会让「谁在推进」这件事失去唯一来源。

### 3. `wakeup create` 是追加，不是替换

同一个单上连续 `wakeup create` 会留下两条规则，两条都会触发，等于巡检频率翻倍。

```bash
multica issue wakeup create <KEY> --kind every --every 30m --expires-in 10h --instruction-file <file>

# 建完立刻核对条数，多出来的删掉
multica issue wakeup list <KEY> --output json
multica issue wakeup delete <KEY> <wakeup-id>
```

期望 `wakeup list` 只返回一条且 `enabled: true`。

### 4. 派单前确认 spec 已合并到 main

子单从 `main` 检出。如果界面规范、产品契约还在 PR 里没合并，子单读到的是**旧基准**，会按旧原型改一遍，然后整轮返工。

派单前的核对：

```bash
git fetch origin main
git show origin/main:.agents/spec/design/modules.json | grep -c create-release   # 期望 1
head -1 <(git show origin/main:.agents/spec/design/design.md)                    # 期望「# 界面设计规范（v2）」
```

任一项不符就先合并 spec 的 PR，再派单。已经派出去的要取消重派，不要指望执行者自己发现。

## 四、三次真实事故

| 事故 | 表现 | 根因 | 代价 |
| --- | --- | --- | --- |
| 巡检唤醒挂在容器单上 | 容器单被置 `blocked`，理由是「依赖未满足」 | 唤醒指令写了「完成收口」，执行者照做 | 一条错误交接，需要人工更正 |
| 同一单建了两条唤醒 | 巡检频率翻倍，多起一条 run | 把 `wakeup create` 当替换用 | 一条误触发的 run 被取消 |
| spec 未合并就派单 | 四张子单按旧原型开工 | 派单前没核对 `main` 上的 spec 版本 | 四条 run 全部取消重派，损失约 30 分钟 |

## 五、派单自检清单

派单前逐条过：

- [ ] 目标是执行单还是容器单？容器单不派执行者。
- [ ] 这张单的文件边界写清了吗？与并行单有没有重叠？
- [ ] 依赖的 spec 已经在 `main` 上了吗？
- [ ] 派完 `issue runs <KEY>` 看一眼：**有且只有一条** running。排队的那条是重复发起，取消掉。
- [ ] 建了唤醒的话，`wakeup list` 是不是只有一条？

## 六、状态推进的判据

| 状态 | 推进条件 |
| --- | --- |
| `in_progress` | 已有 running 的 run |
| `in_review` | 出了 PR，且 PR 里有 `[Result]` 说明改了什么 |
| `in_validator` | 评审通过，且 `pnpm test:acceptance` 有输出 |
| `in_merge` | 评审与验收都通过，无冲突 |
| `done` | 已合并，且 `pnpm check:modules` 与用例集都绿 |

没有对应证据就不改状态。改状态时在单里留一句原因。

## 七、合并闸门的刻度

界面确认这条闸门按「交付」算，不按「合并」算。2026-11-25 lxz 裁定：

| 动作 | 要不要 lxz 确认 |
| --- | --- |
| 单张 UI PR 合进集成分支 `feat/ui-v2` | 不要 |
| `feat/ui-v2` → `main` | **要**，且没有明确确认不许合 |

理由：集成分支不是交付物，`main` 才是。按字面「任何 UI PR 都要确认」会把每一张单都卡一次，而用户要看的是一次完整的界面。

派单与推进时按这张表判断，不要再去问「这张能不能合」。集成分支上的合并只看三条：评审通过、验收用例通过、无冲突。
